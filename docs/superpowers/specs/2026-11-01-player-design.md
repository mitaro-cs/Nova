# Плеер Nova: переписать заново

Дата: 2026-11-01. Часть 4 из 4 в плане «дизайн, работа сервиса, правила интерфейса, экраны».
Статус: черновик на проверку владельцем. Решение владельца: плеер переписываем заново.

## Зачем

Владелец: «всё что угодно вылетает, плеер выглядит ужасно, функционал очень плохой»; отмечены все
проблемы - не запускается, обрывается и буферизуется, перемотка и старт долгие, звук, субтитры,
качество. Сейчас весь плеер - один файл `web/src/lib/player/Player.svelte` (1919 строк), режим
воспроизведения выбирается в браузере по длинной цепочке условий, а ошибки нигде не сохраняются:
журнала ошибок у приложения нет (логи идут только в консоль), поэтому причину «вылета» потом не
увидеть ни владельцу, ни нам.

## Что плеер умеет сейчас (всё это сохраняем)

Четыре режима: `raw` (файл как есть), `remux` (потоковая перепаковка `/play?t=`), `copy` («Оригинал»
в HLS без перекодирования, только Safari/WebKit), `hls` (адаптивное перекодирование, `hls.js`).
Дорожки звука; субтитры WebVTT с настройкой вида; качество (оригинал, авто, высота) и замер
скорости зрителя (`player/speed.ts`); скорость 0,25-2×; кадры перемотки; пропуск заставки и титров
(`markers`); следующая серия с обратным отсчётом; список серий; видео по ссылке (Rutube, VK, свои
сайты, YouTube) и переключение источников; «Смотреть вместе» (`sync`); продолжение с места и
сохранение прогресса; «смотрите на другом устройстве»; проверка «длительность не совпадает с
ожидаемой»; PiP, полный экран, жесты (двойное касание), клавиатура; отчёт `net` в «Сейчас смотрят».
Маршруты сервера: `/api/files/{id}/{info,raw,play,copy/…,hls/…,subs,trickplay,markers}`,
`/api/progress/{id}`, `/api/speedtest`.

## Решение

### Принципы

1. **Один предсказуемый путь выбора режима.** Чистая функция `buildChain(info, caps, pref)`
   (`web/src/lib/player/plan.ts`) по данным файла (`GET /api/files/{id}/info`), возможностям браузера
   (`canPlayType`, `MediaSource`, HEVC) и настройкам зрителя (качество, звук, «уже подвисало») строит
   **упорядоченную цепочку** вариантов `[{mode, quality, why}]`. Остальной код не выбирает режим, а
   идёт по цепочке. Ruling при составлении плана: не серверный запрос `/plan`, потому что возможности
   браузера знает только браузер; сервер остаётся источником сведений о файле (`info`) и потоков.
2. **Падение - не тупик.** Фатальная ошибка или зависание старта (> N с) - автоматически следующий
   вариант цепочки с того же места, без чёрного экрана; сообщение по-русски («Переключаю режим…»).
   Если вариантов нет - понятный экран с причиной и кнопками «Повторить», «Другой источник».
3. **Буферизация лечится качеством, а не ожиданием.** Зависание (`waiting` > порога) → ступень вниз
   (`hls`), возврат вверх только по замеру скорости; без дёрганья туда-сюда (гистерезис).
4. **Журнал, который видно.** Каждое событие (старт, режим, ошибка, зависание, смена режима)
   клиент шлёт через общий канал `POST /api/diag/client` (`kind = "player"`, план надёжности, Task 3);
   сервер пишет в журнал приложения (файл ротации в каталоге данных, 5 × 2 МБ, без адресов и личных
   данных) и в «Управление → Обзор» (часть 3).
5. **Тест на настоящем видео.** Проверка плеера идёт на браузере с H.264 (Edge/Chrome канал
   Playwright, а не встроенный Chromium без H.264), с заготовленными файлами: MP4 H.264/AAC, MKV
   HEVC, 10 бит, несколько звуковых дорожек, внешние субтитры cp1251.

### Модули (вместо одного файла)

`web/src/lib/player/`:
- `session.svelte.ts` - конечный автомат: `idle → loading → ready → playing | paused | buffering →
  ended | failed`; единственный владелец `<video>`.
- `plan.ts` - разбор цепочки с сервера, переход к следующему варианту, гистерезис качества.
- `engine/` - `native.ts` (raw/remux/copy), `hls.ts` (ленивая загрузка `hls.js/light`),
  `link.ts` (видео по ссылке).
- `tracks.ts` (звук, субтитры, их вид), `progress.ts` (место, продолжение, «на другом устройстве»),
  `skip.ts` (заставка, титры, следующая серия), `sync.ts` («Смотреть вместе»), `report.ts` (журнал).
- Интерфейс: `PlayerShell.svelte`, `Controls.svelte`, `Seekbar.svelte`, `Overlay.svelte` (ошибки,
  пропуск, отсчёт), `panels/{Audio,Subs,Quality,Speed,Episodes,Sources,Settings}.svelte`,
  `input.ts` (клавиши, жесты). Страницы `/watch/[id]`, `/watch/link/[id]`, `/room/[id]` используют
  одну оболочку.

Сервер: `api/play.rs` разделить на `plan`, `files` (raw/play), `hls`, `copy`, `subs`, `report`;
`stream.rs`, `hls.rs`, `copy.rs` не переписываем (рабочие), меняем только то, что нужно плану.

### Внешний вид

По эталону Rewind (решение владельца): чёрный фон, капсулы в стиле «жидкого стекла» только малых
размеров, один шрифт Inter, масштаб `--rw`, движение только `opacity`/`transform`. Конкретная
компоновка органов управления - после выбора макета владельцем (макеты готовятся отдельно).

## Решено

- **Макет органов управления - вариант C (выбор владельца, 2026-11-01):** крупные кнопки по центру
  (перемотка назад на 10 с, пауза/пуск в круге, перемотка вперёд на 10 с), сверху название и
  закрытие, внизу тонкая полоса перемотки, время слева, справа значки субтитров, качества и полного
  экрана. Список серий, звук и скорость - в панелях из значков/меню; на ПК та же раскладка, кнопки
  мельче (масштаб `--rw`), клавиатура работает всегда.
- **«Оригинал» (`copy`)** остаётся только там, где HLS родной (Safari, WebKit); на Windows
  (WebView2/Chromium) цепочка начинается с `remux`, затем `hls`. Правило уже действует
  (`CLAUDE.md`), `plan` его просто фиксирует на сервере.
- **Пороги зависания:** старт - 8 с без первого кадра, посреди фильма - 3 с ожидания; значения
  в одном месте (`plan.ts`), правятся по измерениям, а не на глаз.

## Проверка

Юнит: `plan.ts` (цепочки, гистерезис), конечный автомат (переходы, отмена при смене источника).
Сервер: `plan` отдаёт нужную цепочку для сочетаний устройство × кодек × скорость.
E2E на настоящем видео: старт, перемотка, смена дорожки, субтитры, падение режима → автопереход,
продолжение с места; обход экранов не даёт ошибок консоли.
