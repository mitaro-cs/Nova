## Назначение и состав

Nova превращает локальную медиатеку владельца компьютера в сайт для просмотра фильмов и сериалов. Дополнительно есть внешний каталог, воспроизведение по ссылкам, социальные функции и совместные комнаты.

| Часть | Ответственность | Главные файлы |
| --- | --- | --- |
| server | Rust-библиотека fsfy и CLI fsfy serve; HTTP, данные, фоновые задачи | server/src/lib.rs, main.rs |
| web | Svelte 5 / SvelteKit 3, TypeScript, статическая SPA | web/src/routes, web/src/lib |
| web/tv | Отдельный TypeScript-клиент с управлением пультом | web/tv/main.ts, app.ts, nav.ts, player.ts |
| desktop | Tauri 2, окно и трей, интеграция с ОС, обновление | desktop/src-tauri/src/main.rs, update.rs, night.rs |
| desktop/night-light | C#-помощник для ночного режима Windows | NovaNightLight.cs, build.ps1 |
| docs | Инструкции хоста, спецификации, планы и история решений | docs/host.md, docs/superpowers, CLAUDE.md |
| scripts, .github | Подготовка ресурсов, локальные команды и выпуск | Makefile, scripts/fetch-ffmpeg.sh, .github/workflows |

Текущая версия — 0.1.0-beta. Версии workspace, web, desktop, Tauri и двух npm lock-файлов согласованы. Лицензия workspace — AGPL-3.0-only. Видимое имя — Nova; внутренние имена fsfy, app.fsfy, cookie и заголовки сохраняют совместимость данных.

## Запуск и жизненный цикл

CLI создаёт Headless-реализацию Host; Tauri — DesktopHost. Обе используют fsfy::start. Интерфейс Host отделяет сервер от выбора папки, открытия файлов, полноэкранного режима и обновлений ОС.

При запуске создаются каталог данных, SQLite и хранилище картинок, находятся ffmpeg/ffprobe, открываются два HTTP-порта. Общий порт по умолчанию 17480 слушает все IPv4-интерфейсы; порт окна 17481 — только loopback. Если порт занят, выбирается другой. Затем создаётся App с общей инфраструктурой, запускаются сканирование, метаданные, обработка изображений, обслуживание медиакэшей, каталогов и комнат.

Данные Windows по умолчанию — %APPDATA%/app.fsfy. Возможны FSFY_DATA и CLI --data. Сервер хранит fsfy.db, изображения и медиакэши; само видео остаётся в подключённых папках либо попадает в папку приёма.

Rust встраивает готовый web/build через rust-embed. При отсутствии сборки фронтенда server/build.rs создаёт HTML-заглушку: успешная сборка Rust сама по себе не подтверждает наличие рабочего интерфейса.

## Данные и API

SQLite работает в WAL, с foreign_keys и busy_timeout. Db — одно соединение под parking_lot::Mutex, синхронные короткие операции через with и tx. Миграции последовательные, транзакционные, по PRAGMA user_version; последняя описанная схема — 30. Есть специальная совместимость с прежней веткой GitHub и более новыми схемами.

Главные сущности:

- libraries → titles → files: папки, произведения и физические файлы/эпизоды;
- users → profiles: аккаунт и единственный пользовательский профиль;
- progress, watched, watching, dropped, my_list, ratings: просмотр и отметки;
- ext_titles, ext_episodes, ext_seen, ext_marks: внешний каталог и действия с ним;
- links, link_progress: внешние источники и их прогресс;
- reviews, friends, messages, lists и таблицы участников: социальные функции;
- sessions, invites, account_tokens, account_emails, logins: доступ и восстановление;
- settings: конфигурация хоста и интеграций.

Маршруты собраны в server/src/api/mod.rs. Обработчики группируются по account/mail, catalog/resume, discover, links/stream_link, play, social/lists/profile, rooms и admin/stats/diag. Это модульный монолит: общий App, явные SQL-запросы, без отдельного сервиса очередей или ORM.

## Путь локального видео

1. library/inbox подключает папку, копирует перетащенные файлы либо принимает загрузку через *.part.
2. library/scan обходит папки, library/parse распознаёт фильм, сезон и эпизод. Пропавшие файлы получают missing вместо удаления; прежний прогресс сохраняется.
3. library/jobs запускает ffprobe, создаёт кадры и уменьшенные изображения; meta подбирает описания и изображения.
4. API play сообщает возможности файла. Фронтенд player/plan.ts выбирает цепочку режимов с учётом браузера, аудиодорожки, кодека и предпочтений.
5. raw отдаёт файл с HTTP Range; remux перепаковывает поток; copy создаёт HLS/fMP4 без перекодирования видео для подходящих клиентов; hls создаёт адаптивные варианты через ffmpeg.
6. PlaySession управляет состоянием video, таймаутами и переходом к следующему варианту. Движки вынесены в player/engine.
7. player/progress.ts сохраняет позицию примерно раз в пять секунд, при паузе и выходе. badges/progressSync сигнализируют об изменениях на другом устройстве.

Есть субтитры WebVTT, обработка внешних SRT и Windows-1251, дорожки аудио, превью перемотки, главы, следующая серия и ZIP64-скачивание. На уровне App ограничены параллельные тяжёлые операции: два слота перекодирования и восемь перепаковки. Фоновые задачи и процессы обслуживания кэшей требуют особой осторожности при изменениях.

## Внешние данные и видео

meta объединяет IMDb, TMDB и Кинопоиск. discover хранит внешний каталог, подборки и подробности; names/ruwiki/episode_locale дополняют локализацию, directors/franchise — людей и серии фильмов. Часть источников использует неофициальные веб-интерфейсы, поэтому изменение внешней разметки или API может ломать функцию при неизменном коде Nova.

video_search и video_sources подбирают источники; own_sites ищет по каталогам владельца; lordfilm обрабатывает соответствующую интеграцию. api/stream_link извлекает поток и переписывает плейлисты через сервер. video_health учитывает ошибки источников и временно исключает не отвечающие.

outbound содержит проверку публичных IP, DNS-резолвер и ограничения редиректов; stream_link использует этот клиент и дополнительные списки допустимых доменов. Наличие защитного модуля не является доказательством, что каждый исходящий запрос во всём проекте прошёл полный аудит.

## Интерфейс

Основные разделы: главная, фильмы/сериалы, лента и поиск, карточки локальных и внешних произведений, просмотр, комнаты, коллекция и списки, люди/чаты, профиль, управление и страницы входа/восстановления.

Общие части вынесены в lib/ui, title, discover, player, social, profile, account и admin. Состояние — Svelte runes и модули session/catalog/cards/localized; API-клиент централизует ошибки, CSRF-заголовок и однократный повтор безопасного чтения. Каталог кэшируется в памяти вкладки на 15 секунд; тяжёлые части интерфейса загружаются лениво.

ТВ-клиент имеет собственные экраны, hash-маршрутизацию и состояние. Сборка нацелена на Chrome 69, помещается в static/tv и затем в общий build. Сервер определяет телевизор по User-Agent; есть /tv/ и обход через ?full=1. Функции основного интерфейса и ТВ нужно проверять отдельно: общий API не гарантирует одинакового поведения двух клиентов.

## Доступ и приватность

- Argon2id для паролей, SHA-256 токенов в БД, HttpOnly/SameSite cookie.
- Локальная сессия окна привязана к отдельному входу Via и не должна приниматься на публичном порту.
- Viewer и Manager отделяют просмотр от управления; удалённое управление зависит от настройки хоста и включённого TOTP.
- Изменяющие запросы API требуют X-Fsfy: 1; общая middleware добавляет CSP и другие защитные заголовки.
- Есть лимиты регистрации, входа, сообщений и диагностических отчётов; хеширование паролей ограничено двумя параллельными задачами.
- Приватность профиля реализуется на сервере, включая видимость статистики, просмотренного и отзывов.
- Комнаты живут в памяти, синхронизация — SSE + HTTP, голос — WebRTC с серверным обменом сигналами. Перезапуск закрывает комнаты.

## Проверки и выпуск

Сервер: unit-тесты рядом с модулями и интеграционные наборы в server/tests, в том числе безопасность, восстановление, социальные функции, комнаты и реальные медиасценарии. Общие помощники генерируют видео ffmpeg и запускают сервер во временной папке.

Фронтенд: Vitest, svelte-check с fail-on-warnings и отдельный tsc для TV. Playwright использует собственную демо-базу и четыре проекта: WebKit iPhone, Chromium phone, tablet, desktop. Результаты этих проверок в данном окружении неизвестны.

ci.yml описывает проверки сервера, web, E2E и desktop. release.yml отдельно запускается на miaro и тегах v*, собирает Windows x64 и два Mac-варианта. При наличии секрета создаются подписанные автообновления. update.rs скачивает обновление, вызывает остановку сервера и делает резервную копию БД перед установкой.

| Приоритет | Наблюдение | Последствие и следующий шаг |

| Высокий | Running::shutdown останавливает HTTP и туннель, но фоновые tokio::spawn из start не сохраняются и не получают сигнал остановки | Они удерживают Arc<App> и соединение БД. Архитектурные ограничения, не доказанные дефекты: одно синхронное соединение БД может стать узким местом при росте нагрузки; крупные admin/discover/social модули усложняют изменения; глобальные статические кэши требуют внимания при нескольких экземплярах App; внешние парсеры требуют живых контрактных проверок. Измерений, подтверждающих текущую проблему производительности, нет.

## Правила для последующей работы

Сохранять app.fsfy и внутренние идентификаторы; новые изменения схемы добавлять миграциями. Проверять права в обработчиках, а не только скрывать кнопки. Различать аккаунт и профиль, локальные произведения и внешний каталог, локальные файлы и ссылки. Любое изменение плеера проверять отдельно на Safari/WebKit и Chromium, с перемоткой, другим аудио, восстановлением позиции и переходом на резервный режим. Перед выпуском собирать оба интерфейса, запускать предусмотренные проверки и проверять установщик Windows.

Первыми практическими задачами после подготовки среды будут запуск существующих проверок и проверка корректной остановки/резервного копирования. После этого имеет смысл исправить Windows-поиск E2E-бинарника, порядок публикации релиза и небольшие подтверждённые ошибки. Продуктовый код при изучении не изменён.
